# Backend

The backend rules in full: what Atom owns and enforces, and where a project's code and settings go. [AGENTS.md](../AGENTS.md) lists them in short and says which are enforced, which are rules and which are defaults; this page has the detail. Read the section for the area you work in before changing it.

# Core
What Atom owns and enforces in every project. A project never edits these paths; it changes behaviour through settings (below).

## Ownership and sync
- Atom owns every unsuffixed path (core: `function/`, `router/`, `docs/`, `script/`, `static/`, `files/` and root files such as `config.py`, `main.py`, `sync.py`, `AGENTS.md`, `ruff.toml`, `Dockerfile`, `.dockerignore`; full list: `SYNC_FILES`/`SYNC_FOLDERS` in `sync.py`). The project owns `*_extend` paths and `config_extend.py`, which the Atom repo doesn't have (sync creates them). Shared: `.env` (project), `requirements.txt` and `.gitignore` (merged), `.github/` (per repo).
- Never edit core unless asked for a framework change: sync overwrites it and deletes other files in Atom folders. Refactors, renames, cleanups and lint fixes touch project files only; if core blocks the work, solve it in project paths or report it.
- `python3 sync.py` (Windows `py sync.py`, from a new shell outside the venv), from the Git root, after committing, with the app stopped. `--no-venv`: files only; `--no-outdated`: no PyPI lookup (CI: both); `--status`: versions only, changes nothing. New project: empty folder, `git init`, download `sync.py`, run it.
- Sync replaces core, never modifies existing `*_extend` files or `.env`, and creates whatever is missing: `*_extend` folders each with a `readme.md`, a starter `config_extend.py`, `tests_extend/__init__.py` (needed for test discovery), a commented `.env`.
- Version: `ATOM_VERSION` in `sync.py` (printed at startup, returned by `/info`), raised by hand in Atom with its entry at the top of `CHANGELOG.md`; CI then tags `vX.Y.Z` and creates the GitHub Release. Sync takes Atom's latest `main`, or `--ref vX.Y.Z` for a fixed version.
- `requirements.txt` and `.gitignore` each have two headers: `# atom` (Atom's, reset every sync, never edit) and `# extend` (the project's, kept). `# extend` packages: pinned `==`, only what the code imports directly, no comments. Sync drops packages Atom no longer lists (a project still using one adds it to `# extend`) and `# extend` duplicates of Atom's, keeps the last repeated line, sorts, warns on unpinned lines, lists newer `# extend` versions and rebuilds `venv/` to match exactly. `.gitignore` `# atom` is deny-all plus Atom's paths: a top-level path is committed only if named `*_extend` or listed under `# extend` (`!<folder>/` and `!<folder>/**`).

## Request path and config_api (the middleware enforces it before the route; never re-check in a route)
- Request path: middleware applies `config_api` → route → `func_*` → DB → `{"status": 1, "message": ...}`.
- Every route needs an entry with a unique `id` (200+ for project routes) and `auth`; startup fails on a missing entry, an entry without a route, a repeated `id`, a project route under 200, an `/admin/*` route with neither `user_check_permission` nor `user_check_role`, or a role, permission or user check with an empty `auth`.
- `auth` lists the credentials a route accepts (401 otherwise): `[]` public, `["jwt"]` a JWT access token (people), `["api_key"]` an API key (machines), `["jwt", "api_key"]` either; both come as `Authorization: Bearer`. `user_check_role` and `user_check_permission` are independent: a route sets either or both.
- `user_check_role: {"mode": m, "roles": [..]}` (403); `user_check_deactivated`/`user_check_deleted: {"mode": m}`. Every route with a credential gets both from `config_api_global_user_check_deleted`/`_deactivated` (default `token`) unless it sets its own, so a route never repeats them. `m`: `token` (fastest, stale until re-login), `redis` (cached), `realtime` (DB each request; admin and destructive routes), `inmemory` (startup snapshot, single worker).
- `user_check_permission: {"mode": "token"}` (403): only users whose `users.permissions` holds this route's `id`, whatever their role; every `/admin/*` route uses it, and root holds every admin id. Its label is its path (`/info` `int_mapping.master.users.permissions`). Grant only through `/admin/user-update`. Flow in [auth-permission.md](auth-permission.md).
- Each schema's `control` lists which tables Atom's object routes may use (`public_create`, `public_read`, `private_read`, `my_create`, `my_read`, `my_update`, `my_delete`, `my_delete_all`, `admin_create`, `admin_read`, `admin_update`, `admin_delete`; closed unless listed; `["*"]` only in admin lists, Atom's master default; the admin routes also need their id granted; a database without a schema is closed, [config.md](config.md#control)); a table written only through feature routes is in no write list. An `"auth": []` route that writes data checks a shared secret from `.env` in its function; never re-enable an Atom route that ships `is_active: False`.
- `rate_limit: {"mode": "redis"|"inmemory", "limit": N, "window_sec": S}` (429); `cache: {"mode": "redis"|"inmemory", "ttl_sec": S, "is_per_user": bool}`; `is_connection_param: True` allows `?connection=<name>`; `is_active: False` → 404; `is_log_api: False` keeps requests out of `log_api`.
- WebSocket entries take only `id` and `is_active`; the socket function checks both and authenticates itself (token as first message).
- `request.state.user` = decoded token or API key owner (its `users` columns in `config_users_token_column`) or `{}`; user id and role come only from it, never from params. Row ownership and other rules `config_api` can't express go in a `func_*`.

## Data and security
- Rows only through `func_postgres_create/read/update/delete` (a route that takes the table or columns from the request first calls `func_object_access`, the gate of Atom's table routes: `control` access lists, `/my` ownership, audit and `write_blocked` columns on writes, and the `read_blocked` columns it returns for reads) (inside a feature's transaction too: pass its `client_postgres_conn`), not hand-written `INSERT`/`UPDATE`/`DELETE` or plain `SELECT`: they check columns, types and ownership (`created_by_id`; CRUD and ownership docs in `docs/`) in one round trip. Hand-written SQL only for what they can't express (joins, aggregates, row locks). Never `is_trusted=True` with request data.
- SQL values bound as `$1, $2`, never in f-strings; identifiers only after `^[a-zA-Z_][a-zA-Z0-9_]*$` or an allow-list, quoted. Postgres only through asyncpg (`app_state.client_postgres_dict[...]` in the app, `func_client_postgres` or `asyncpg` in scripts; no psycopg or SQLAlchemy); reg* types: `$1::text::regclass`, `to_regclass(x) IS NOT NULL`. Redis names `api_response`, `user_state`, `ratelimiter`, `queue` are Atom's.
- Speed: every list pages after a cursor by default (`docs/crud.md` Paging): request `limit`, `order` (default `id desc`, `id` added last) and an optional `after`, or `page` to jump within `config_page_offset_max` rows (never both); response the rows and `after` (`null` on the last page); built only with `func_page_keys`, `func_page_order_sql`, `func_page_after_where`, `func_page_offset` and `func_page_after_next` (limit + 1 rows read); never an uncapped `OFFSET` or a total `count(*)`; an index matching each list's filter and sort (`btree(col,id)`); read what a request needs in one query (one row for several checks, `= ANY($1)` for ids, many rows updated with one `UPDATE ... FROM unnest(...)`), not one query per check or item; work out what depends only on a column or type once, before the row loop; a transaction only around statements that must succeed together.
- Atom's logs, OTP and `script_run` are in no `public_*` or `my_*` write list, so only the `/admin/*` object routes (the tables in `admin_*`, `["*"]` in Atom's master, for users granted their ids) reach them; the database refuses updates to the tables in `control.row_update_disabled` (`log_api`, `api_key`, `log_users_password`) and deletes from those in `row_delete_disabled`. A project keeps that on Atom's tables.
- Pool connections go back without a session reset: never change session state in project code (no plain `SET`, `set_config(..., false)`, `LISTEN` or unreleased advisory lock); use `SET LOCAL` inside a transaction, and run SQL someone typed through `func_postgres_acquire_clean`.
- Responses over 1 KB are gzipped by Atom when the client accepts it: never compress in a route or add compression middleware; a route sending bytes it already compressed sets `Content-Encoding`. Measured numbers: `docs/performance.md`.
- Request bodies over `config_request_body_max_kb` (10 MB; multipart `config_request_form_max_kb`, 100 MB) get 413 before they are read: a project needing more raises the setting in `config_extend.py`, never reads around it; bigger files go straight to storage with a presigned upload.
- Production: `config_token_secret_key` 32+ bytes. With `config_uvicorn_workers` > 1: no `inmemory` mode for caches, rate limits or user checks, and `/my/message-socket` stays inactive (startup fails).
- Never fill missing business data with placeholders (names, dates, codes, branches) or ship demo data: leave it empty and say so. Deploy settings (infrastructure templates, CI workflows, hosting settings) set only `config_*` keys that Atom or `config_extend.py` reads.

## Scale and speed (defaults: a project keeps working at 100× today's data)
- Each screen read is one SQL statement through the pool: several result sets in one statement as JSON subqueries (`COALESCE(json_agg(t), '[]')`), no transaction around a single read, a timeout on every query.
- Every filter, sort and search column has an index in `config_postgres_schema_master` (`btree` for equality, ranges and sorts, `gin_trgm` for contains-search); a list's `ORDER BY` matches an index, with `id` as the cursor's tie-break (a descending sort with empty values last: `btree(col desc nulls last,id)`).
- Aggregates in SQL; no `OFFSET` past the first pages, no `count(*)` per page; exports streamed with a cursor, never built in memory.
- Sync and import scripts write in batches inside a transaction and resume from `tmp/<script>/`.
- Route params with `strict=True, strict_types=True, reject_unknown=True`.
- Optimise only what is measured slow, or what breaks these.

## Security (rules: check them in every review)
- Secrets only in `.env` (never committed, never in `config_extend.py`, `files_extend/`, a page's JS, logs or error messages); a key that leaked is rotated, not just removed.
- Every route's access is in `config_api` (`auth`, role, permission); an `"auth": []` route that writes checks a shared secret from `.env`; no route returns more columns than its screen needs (never `password` or tokens).
- SQL values bound (`$1`), identifiers allow-listed; pages escape every value before `innerHTML`; nothing secret in a URL (tokens travel in the `Authorization` header).
- Uploads checked for type and size, stored through Atom's storage helpers; downloads stream through Atom's export.
- Local test servers run with `config_is_postgres_schema_init=false` against a shared database, so editing `config_extend.py` never changes its tables; schema changes reach it only with the deploy.

## Atom's own files
- Atom's own files (core): headers, lowercase singular, no module docstrings (routers `# import`/`# router`/`# api`; functions `# import`/`# function`); one name per import line (`from x import a`, then `from x import b`). Project files follow the project's own style, except scripts (below).
- Atom's `script/` `# logic`: one top-level helper per named step (`noun_verb`: `task_claim`, `batch_fetch`), keyword-only, getting `# config` values as arguments (`# setting` constants may be read directly); `main()` is last, at most 30 lines, defines no functions, reads like steps (read config, open clients, call helpers, close in `finally`); async scripts keep `main()` sync and call `asyncio.run(...)` once. CLI flags and process state (`sys.argv`, argparse, `os.environ.copy()`) are read in `# logic`: an `args_read()` helper or `main()`. Exception: `func_run_broker` callbacks take its positional arguments.
- Atom's `script/` holds only scripts that work in every project: imports are stdlib, packages, `config` and `function` (never `files`, `router` or `*_extend`; `sync.py` stdlib only); outside values are read only in `# config`; writes go only to `tmp/` and Atom's own tables. Scripts tied to a project's tables go in `script_extend/`.

# Extending Atom
A project's own code and settings: `*_extend` paths, `config_extend.py`, `.env`.

## Where code goes
Name files after the feature across folders: `router_extend/<f>.py`, `function_extend/<f>.py`, `files_extend/<f>.py`, `static_extend/<f>/`, `docs_extend/<f>.md`, `tests_extend/test_<f>.py`; a big feature splits into `<f>_<part>.py` (`billing_invoices.py`), never unprefixed helper files.
1. API → `router_extend/<f>.py` (`router = APIRouter()`): read params, call one `func_*`, return; no business logic, no permission checks.
2. Logic → `function_extend/<f>.py`: `func_*`, available as `app_state.func_*`.
3. Files → `files_extend/`: shared constants and `param_specs` (import `files_extend.<module>`), JSON, prompts, templates (read by path from the project root). Read-only at runtime.
4. Web pages → `static_extend/` (see Pages).
5. Config → `config_extend.py`. Jobs → `script_extend/` (enqueue with `app_state.func_producer`, on the Postgres queue unless it can't keep up: [queue.md](queue.md)); a queued job runs at least once and may run twice, so it must be safe to repeat. A job on a timer: `config_schedule_script_<script>` (`off` by default in code) and its work inside `async with func_script_run(...)` ([docs/schedule.md](schedule.md)); never a loop in `func_extend`. A script that runs until stopped is `# type: continuous` (named `worker_<x>` when it polls for work, `consumer_<x>` when it listens on a queue), runs as its own process and is never scheduled (startup refuses it). Tests → `tests_extend/` (`unittest`, with `__init__.py`). Docs → `docs_extend/<f>.md`: short, behaviour and business rules only, no SQL or code dumps. Packages → `requirements.txt` under `# extend`.
6. Temporary and generated files (exports, scratch, downloads, compile output, logs; from routes, functions and scripts alike) → `tmp/<feature>/` (gitignored), created with `os.makedirs(..., exist_ok=True)`; never tracked folders or the system temp folder (`/tmp`, `%TEMP%`; pass `dir="tmp/<feature>"` to `tempfile`). Each feature deletes its own files when done (`config_is_tmp_reset`, default false, wipes `tmp/` at start); data that must survive goes in the database.
- Data users change at runtime (an option list edited from a page, a setting saved from the UI) lives in the database, never in a file: a deploy, `git pull` or fresh container replaces files. A setting is one row in Atom's `config` table (`key` unique, `value` jsonb; upsert with `ON CONFLICT (key) DO UPDATE`); other row-shaped data gets its own table in `config_postgres_schema_master`. Files users download (templates, exports) are built in memory on request, or written to `tmp/`.
- Option lists (a page's selects and dropdowns), by who edits them. Developers: `config_options` (list or `.txt`/`.json` file in `files_extend/`), served by `/info`. Users: a table in `config_postgres_schema_master`, designed by the project; reads through the feature's route or the table in `control.public_read` / `private_read`; writes only through the feature's route (`config_api` role check, `realtime` mode) calling a `func_<feature>_*` that validates, with `created_by_id`/`updated_by_id` from `request.state.user`; the table is in no `control.my_*` write list (`my_create`, `my_update`, `my_delete`, `my_delete_all`) so `/my/object-create` can't bypass it.

## Reuse Atom (search `function/` for a `func_*` before writing a helper, client or pool)
- Databases, any number per type: `.env` lines `config_<db>_url_<name>=<url>` (`<db>`: `postgres`, `mssql`, `redis`, `clickhouse`; e.g. `config_postgres_url_master`, `config_mssql_url_erp`) fill `config_<db>_url_dict`; Atom opens one pool each at startup and closes it at shutdown: `app_state.client_<db>_dict["<name>"]` (default `master`; `func_mssql_client_read` and `func_clickhouse_client_read` 400 on an unknown name). A new database is a new `.env` line, never code. A route letting the caller pick one names the param `connection` (query or body, default `master`, unknown 404), never `postgres`, `mssql`, `clickhouse` or `database`. On the admin query runners only role 1 picks it: a project that opens one to other roles gives them `master` only (403 otherwise), so its other logins stay with admins.
- Other clients, opened at startup and closed at shutdown: `client_mongodb`, `client_s3`, `client_ses`, `client_sns`, `client_openai`, `client_gemini`, `client_anthropic` (Claude), `client_http` (shared HTTP session), `client_azure_blob`/`_email`/`_sms`, `client_msgraph`, `client_sftp`, queue producers. App code never opens its own pool, connection or SDK client (pool sizes: `config_postgres_pool_*`, `config_mssql_pool_*` in `.env`, one database's with a `_<name>` suffix such as `config_postgres_pool_max_size_test`; anything else is a framework change, never a second pool). Scripts open their own with `func_client_*` or the driver, reading URLs from `.env` by key.
- Helpers: params `func_request_param_read`; errors `func_api_error`; rows `func_object_access`, `func_postgres_create/read/update/delete`; SQL `func_postgres_query_runner_read`, `func_mssql_client_read`, `func_mssql_query_runner_read`, `func_clickhouse_query_runner_read`; CSV `func_postgres_export`, `func_mssql_export`, `func_clickhouse_export`, `func_postgres_read_export`, `func_csv_response`, `func_postgres_import`; files `func_blob_upload_file`, `func_blob_upload_url`, `func_blob_delete_all`; email and SMS `func_email_send`, `func_otp_send_email`/`_mobile`; jobs `func_producer`, `func_run_broker`, `func_background_run`; one-worker sections `func_postgres_advisory_lock`; Claude JSON `func_anthropic_json`.
- Exports: every CSV download, Atom's and a project's, goes through `func_<db>_export` (`postgres`, `mssql`, `clickhouse`; a new database type gets its own in Atom first): one read query, read with a cursor and streamed, at most `config_export_limit` rows (the only row limit, in `config.py`; a user may ask for fewer with `limit`, more is a 400; pages read the maximum from `/info` `export_limit`), returned with `func_csv_response`. A project keeps its own export route (`/<feature>/export`, its params and checks, passing an optional `limit` through); behind it, it writes only its query (filters, permissions), then calls Atom's function: never its own CSV streaming, row limit or count before the download. An export is the data as stored: the header is the query's real column names (a join names a clashing column `"<table>.<column>"`), values as they are, never renamed or relabelled (codes stay codes, ids stay ids).
- Missing in Atom: write a project `func_<feature>_*` (never a `func_<atom_area>_*` name such as `func_mssql_*`, which a later Atom may add) or ask for a framework change.

## Settings
- Every `config_*` from `config.py`, then `config_extend.py`, then `.env`/environment (wins) ends up on `app_state.config_*`; new names work too. Env values are typed by the existing default (else true/false, int, JSON, string); lists become tuples.
- `config.py` sections: one `# <topic>` per feature or system; 4 or more related keys may get their own section (`# log_api`, `# otp`), fewer stay in the closest one.
- On/off settings are named `config_is_<what>` (`config_is_log_api`, `config_is_pgweb_enabled`, a project's `config_is_<feature>_<what>`), default in code, set with `true` or `false` (also `1`/`0`, `yes`/`no`, `on`/`off`; any other value, empty included, stops startup).
- Script schedules are `config_schedule_script_<script>` (`off`, `every 6h`, `daily 02:00`, `every 3d 02:00`, `weekly sun 02:00`, `monthly 1 02:00`, in `config_schedule_timezone`; any other value stops startup); how long a table's rows are kept is its entry in the schema's `control.retention_day` (none keeps them); `config_retention_day_user_soft_deleted` is the days before a soft-deleted user's data is purged.
- `.env`: secrets, URLs, machine flags; one `config_x=value` per line, no quotes, comments on their own lines (`docker --env-file` keeps quotes and inline comments in values). Prefer `config_extend.py` for a value that is neither secret nor different per environment (a root page path, signup roles): it is then in Git and the same everywhere. A guideline, not a check: `.env` still overrides it where a machine needs to. Developer machines: `config_is_prod=false`; `config_is_pgweb_enabled=true` only there.
- `.env` order: `# atom` (Atom's keys the backend uses), `# extend` (the project's keys the backend uses), then one `# script.<name>` per `script_extend/` script (file name without `.py`) listing every key it reads, with Atom's plain names, so that section alone runs it elsewhere. `# atom` and `# extend` are active; script sections are fully commented out and uncommented where the script runs (backend and scripts load the same file: an active copy overrides a backend key, an active `config_<db>_url_<name>` opens a backend pool).
- `config_extend.py` has three sections, in order: `# base` (only `from config import config_x as base_config_x`; a base import named `config_*` fails startup), `# atom` (every value of a setting Atom's `config.py` defines: its dicts extended and plain overrides such as `config_root_html_path`), `# extend` (settings only this project has: `config_schedule_script_<script>`, `config_is_<feature>_<what>`). The test: the name is in Atom's `config.py` → `# atom`, else `# extend`; no other sections, and no other comments (explanations go in `docs_extend/`). Define each `config_*` once. Project limits and constants are not config: function default parameters or `files_extend/`; browser-only values (cache hours) in the page JS.
- Atom's settings are flat, one plain value each, named `config_<area>_<what>[_<name>]` (`config_cache_row_limit_<name>`); the only dicts are `config_options`, `config_users_role_label`, `config_postgres_schema_<name>` (one per database) and `config_api`. A project's own settings follow the same rule.
- Extend, never replace: `config_x = {**base_config_x, "key": value}`, spread at the top level only; to change one of Atom's keys write its whole value (never `**base_config_x[key]`). `config_postgres_schema_master`: `{**base_config_postgres_schema_master, "table": {**base_config_postgres_schema_master["table"], "<table>": {"column": [...]}}, "control": {**base_config_postgres_schema_master["control"], "my_read": [*base_config_postgres_schema_master["control"]["my_read"], "<table>"]}}`; columns added to an Atom table: `"<atom_table>": {"column": [*base_config_postgres_schema_master["table"]["<atom_table>"]["column"], {...}]}`, never `.append`.
- Startup fails if `config_extend.py` drops Atom's entries from `config_api` (routes), `config_postgres_schema_master` (`table`, `control` with `control.extension`, `sql` and their entries) or `config_users_role_label` (codes); values and labels may change, additions are free.
- New tables: column spec in Atom's extend docs in `docs/`; owner columns get `"index": ["btree(created_by_id,id)"]`.
- After a sync that raises Atom's major version, follow its entry in `CHANGELOG.md` (marked **Upgrade**) (startup names any removed setting still set).

## Routes and functions
- Path (a default, not a rule): `/<feature>/<thing>-<verb>`, naming what the route reads or writes, the verb last (`read`, `read-single`, `create`, `update`, `delete`, `export`): `/order/order-read`, `/order/order-read-single`, `/order/order-export`, `/order/option-read`, `/report/dashboard-read`; not a bare `/order/read`, which hides what comes back. `my-<action>` for the caller's own rows (`/order/my-order-create`). One route per screen task, not one per chart, and no `?kind=` switch between unrelated reads. Another style is fine where it reads better (a domain verb such as `/case/close`, an outside system's name); keep one style within a project.
- Use Atom's routes before writing one, as they are: a page reads a table through `/private/object-read` and `/private/object-read-export` (the table in `control.private_read`; its filters as Atom's filter list, `docs/crud.md`), and writes through the `/my/object-*` routes below. Keep their Atom defaults: no `config_api` override (deactivated and deleted users are refused by Atom's global checks), unless the project has users who must not reach them. They also cover a board (`group_column` + `group_values`: the first page of each value in one call) and counts by columns (`/private/table-column-groupby`). Write a project route only for what they can't do: several different lists in one statement, joins, computed filters or business checks.
- A page may write through Atom's `/my/object-create`, `/my/object-update` and `/my/object-delete` (the table in `control.my_create`, `my_update`, `my_delete`): each write is limited to the user's own rows (`created_by_id`, or a column whose `ownership` lists the action). Write a feature route only when a write needs more than ownership (validation, several tables, a rule about who may change what).
- Route: `async def func_api_<area>_<name>(*, request: Request):`, then `app_state = request.app.state`; use only `app_state.func_*/config_*/client_*`, `request.state.client_postgres`, `request.state.cache_postgres_schema`; never import from `function`.
- Params only via `await app_state.func_request_param_read(request=request, mode="query"|"body"|"form"|"header", param_specs=[...])` (shared specs in `files_extend/<f>.py`); add `strict=True, strict_types=True, reject_unknown=True` to refuse unknown or mistyped params (recommended). Spec keys: `name`, `type` (`str`, `int`, `float`, `bool`, `list`, `list:int`, `dict`, `file`, `any`), `required`, `default`, `allowed`, `minimum`, `maximum`, `min_length`, `max_length`; with `is_connection_param` add `{"name": "connection", "type": "str"}`. Never declare the middleware flags `is_disable_cache` and `is_background`.
- Return `{"status": 1, "message": result}`; errors `raise app_state.func_api_error(message=..., status_code=...)` (plain `Exception` → 400). List routes with `app_state.func_app_route_list(app=request.app)`.
- Functions: `func_*`, keyword-only, unique across `function/` and `function_extend/` (duplicates fail at import); `_*.py` and subfolders are not loaded; import from defining modules (`from function.request import ...`). `function_extend/<f>.py` defines only `func_<f>_*` (helpers shared across features: `<project>.py`, `func_<project>_*`).
- Who may see a row and who may change it come from one shared helper, and a caller's own filter never removes an owner restriction; cast ids and codes from request bodies before comparing.
- `app_state` names say what they hold: `func_`, `config_`, `client_`, `cache_` (kept for reuse, safe to lose), `buffer_` (rows waiting to be written), `runtime_` (tasks, locks, counters). A project adds none: its data goes in `app_state.extend`.
- Optional `func_extend(*, app_state)` runs once after Atom's clients are ready (its return is `app_state.extend`); `func_extend_shutdown(*, app_state)` runs before they close: open and close project clients and pools there (never leave a pool unclosed). Never edit `main.py` for this.

## Users, roles and permissions
- Roles: 1 is Atom's admin (every `/admin/*` route); a project route lists 1 only when an admin needs it (e.g. to call it from Postman), not by default: an admin otherwise tests it with their own account of that role. Project users start at 2 (one kind of user: role 2, routes allow `[2]`); each new kind takes the next number and is added only to the routes it may call. Label every role used in `config_users_role_label` (`{**base_config_users_role_label, 2: "User"}`); who may log in: `config_login_allowed_roles` (`config_signup_allowed_roles` for self sign-up).
- Users: `/admin/user-create` (role, username, password, plus any `users` column not `write_blocked` for `my` or `admin` and not in `config_users_update_alone_column`, in one insert), `/admin/user-update`, `/admin/user-delete` (`mode`: `hard`, `soft`, `restore`), `/my/user-update`, `/my/user-delete` (`mode`: `hard`, `soft`); users, logins and permissions live in `master` only (another database's `users` is a plain table); an app's own user management grants `/admin/user-create` and `/admin/user-update` (deactivate with `deactivated_at`); read with `/my/profile`, `/private/user-read` (the list, `config_users_private_read_column`) and `/admin/object-read`. The generic object APIs refuse `table=users`; never write a project user create, update, password, email or delete API (add columns to `users`, see Settings). Every `users` column is updatable unless it is an audit column (`created_*`, `updated_*`, `deleted_*`: Atom's), its `write_blocked` lists `my` (admins only), or lists `admin` (nobody, through the APIs) ([users columns](config.md#users-columns)).
- Settings, not code: most of an app needs only `config_extend.py` and grants. Shared reads: the table in `control.private_read`. Own rows: `/my/object-*` (the table in `control.my_*`). Anyone's rows, for selected users: a grant of the admin object route ids (67 read, 66 update, 72 delete). The app's users: grant 69 (`/admin/user-create`) or 70 (`/admin/user-update`: profile, password, deactivate); the page side is [user-management.md](user-management.md). Grant with `/admin/user-update` (`permissions`); a granted user's page sees the ids in `/my/profile` `permissions` after a token renewal.
- Admins have limits too: `/admin/*` writes check role, deactivation and permission `realtime` and are rate limited (a new admin write route does the same; `tests/test_admin_guards.py` lists them); audit columns (`created_*`, `updated_*`, `deleted_*`) are Atom's, never a request's; the SQL write runner takes one `INSERT`/`UPDATE`/`DELETE` (with `WHERE`); nobody changes their own role, permissions or deactivation.

## Scripts
- Scripts (and `sync.py`): `# type: job` (runs once and exits; may be scheduled) or `# type: continuous` (runs until stopped: a worker or consumer, its own process, never scheduled) as the first line, then `# command: <how to run>` (one line per way to run), `# info: <one line>` (optionally followed by short `# - step` bullet lines), then `# import` (packages, then project code: `config`, `config_extend`, `files*`, `function*`; a setting with a default in code comes from here, `from config import config_options`), `# config` (only what differs per machine, read only here: `load_dotenv(os.environ.get("ATOM_ENV_FILE", ".env"))`, then one `name = os.getenv("<exact .env key>")` per value: URLs, keys, passwords, any `config_*` whose default is `None`; nothing else), `# setting` (hard-coded values, UPPER_CASE), `# logic` (helpers, then `main()`), `# main` (only `if __name__ == "__main__":` calling `main()`). Every section present, even empty; one blank line between `# type`, the `# command` lines (kept together), `# info` and every section header; no blank lines inside `# config`/`# setting`.
- A script imports only packages in `requirements.txt` and sets its exit code with `sys.exit(...)` inside `main()`. Tests write temporary files only under `tmp/` and build project tables with `func_postgres_schema_init` from `config_postgres_schema_master`.
- A `script_extend/` script needs only the sections above; how its `# logic` is organised is the developer's choice.
- A `script_extend/` script is one `.py` file per job; it may import stdlib, packages, `config`, `function` and the project's own `function_extend`/`files_extend` (move helpers there when a script grows); outside values only from `config.py` or the environment, in `# config`; runtime data and resume state in `tmp/<script>/`, kept while a run can resume and deleted once it succeeds.
