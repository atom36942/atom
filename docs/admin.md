# 🛠️ Admin Toolkit & Built-in Web Interfaces

Atom includes high-privilege administrative utilities, schema inspection tools, data import runners, and embedded zero-dependency web interfaces.

---

## 1. Built-in Web Interfaces

Atom embeds single-page browser interfaces in `static/`. The page at `/` (`config_root_html_path`) lists them all. They share one dark theme, and the ones that log in (API, Monitor, Admin, Message) are built on the same four blocks (look, account, account header, dialogs), copied unchanged between them: see [Reference code](frontend.md#reference-code). Logged in, the header shows **Sync** and an avatar with the username's initials, opening **My profile**, **Login details** (Sign in: username, password with a pencil to change it; Account: ID, role, permissions) and **Logout**; the Sync dialog shows what the page keeps in the browser and downloads it again.

### Home (`/`)
Served at `/`: a table of every page, from `GET /static-pages` (public, kept out of `log_api`). A page is a top-level `.html` file or a folder with an `index.html`, opened by name at `GET /page/<name>` (`<name>.html` or `<name>/index.html` → `/page/<name>`; public, revalidated on every load), in Atom's `static/` and the project's `static_extend/`, the home page included, whatever the name; other files (CSV, scripts, images, folders without `index.html`, deeper pages) are skipped but still served at `/static/...`. Two pages with one name stop startup. Each `/static-pages` entry is `{name, url, folder, path}`; with `config_is_home_atom_listed=false` it lists only `static_extend/` pages, so the home page shows just the project's (Atom's still open at `/page/<name>`). Each row shows the page's name (its file or folder name with the first letter capitalized) and its path; clicking the row opens the page in a new tab. Search with `/`, Enter opens the first match.

### Atom (`/page/atom`)
A public page about Atom for anyone, with no login and no call to the server: what it does in plain words, a story per feature, its speed, the five checks on every request, the ways to sign in, the built-in pages and one update for every app, drawn by particles that take the shape of each part; a link to the GitHub repository.

### A. API (`/page/api`)
- **Live Endpoint Introspection**: Dynamically displays all endpoints, schemas, and parameter requirements.
- **Interactive Request Runner**: Test GET, POST, PUT, DELETE, and WebSocket connections with headers and request payloads.
- **cURL Importer**: Paste raw curl commands to auto-populate request inputs.
- **Multi-View Response Inspector**: Tree view, raw JSON, and tabular renderers.
- **Login**: the page works logged out (public routes). **Log in** opens the runner of `POST /auth/login-username-password` (`PAGE.login`), so any user logs in, admin or not, with or without a role, and then sees what the backend allows; running any `/auth/login-*` route logs the page in, and running `/my/token-refresh` keeps the new token. localStorage `api` = `{v, token, user, synced_at}`; the OpenAPI spec is the IndexedDB record `openapi`, downloaded on first open and by every sync, so the page opens without waiting; the responses stay in memory.

### B. PgWeb (`/page/pgweb`)
Lightweight browser-based PostgreSQL database manager:
- **Schema & Table Inspector**: View tables, columns, indexes, and constraints.
- **Query runner**: the **SQL** tab of the sidebar opens it; runs queries in the browser and shows the results as a table; the editor and the results are cards on the same grey backdrop as the Rows tab; the bar: Explain, Analyze, **Download** and Execute on the left; what is happening (running…, canceled) and **Reset** (back to the default SQL) on the right. A result is a card headed "Query result" with its rows and time under the title (`10 rows · 5.0 ms`) and a **download icon** on the right. **Download** streams every row the query returns straight to a file (the server runs it again; nothing is shown in the table, no row limit: for large exports), in one of four formats: **CSV**; **SQL dump (COPY)**, a psql script as `pg_dump` writes it (`CREATE TABLE`, then `COPY ... FROM stdin` with the rows), which `psql -d <db> -f file.sql` loads into another PostgreSQL, the fastest way; **SQL INSERTs**, the same with `INSERT` statements of 500 rows each, which any SQL client runs; **JSON Lines**, one JSON object a line. The SQL formats ask for the table to load into (the query's first `FROM` table, else `query_result`) and whether to include `CREATE TABLE` (the result's column names, a repeated one as `_2`, and types without length, so every value fits; a result has no keys or indexes); they need SQL that reads rows (SELECT, WITH, VALUES, TABLE). **Compress with gzip** adds `.gz`, compressed in the browser as the rows arrive. The file name follows the format. The result card's download icon saves the rows shown as CSV, JSON or XML. The table holds at most 10,000 rows or 16 MB of data, whichever comes first; the message says so (`10,000+ rows · showing first 10,000`, or `(16 MB limit)`). Reset is always shown, greyed out until there is something to reset, then red. Every query that runs successfully with **Execute** is saved in the SQL tab's **history** (never a failed one, nor Explain, Analyze, row edits or the page's own reads), newest first: its SQL on one line with how long ago, rows and time (hover for the whole SQL). Clicking one loads it into the editor without running it; the same SQL run again moves to the top. Each has a trash icon on hover, and the History header's trash clears them all after a confirmation. The history stays in this browser (localStorage `pgweb-sql-history`, never sent to the server), one list per database (host, port and name): the last 50, each up to 10,000 characters, for the last 10 databases used.
- **Theme**: light by default; the sun/moon button in the header switches it, saved as `theme` in the `pgweb` localStorage key (set before the page draws).
- **Sidebar**: on the same grey backdrop as the grid, **Tables**, **Views**, **Mat** (materialized views) and **SQL** as one segmented control that switches with a quick 0.1 s fade (hover tints it faintly, the open one stays blue under the pointer); a new connection opens on Tables (a reload keeps the open tab). Under it, one card holds the list, then its footer: the list's count (`204 tables`, `12 of 204 tables` while searching) and the **Search** box with its icon (it searches the open tab's list; a red × clears it); hover a name and click its copy icon to copy it without opening it.
- **Data Browser**: Browse, sort, and filter live table data, 100 rows per page by default (pick 50, 100 or 500; remembered). The filter icon opens the **Filter rows** dialog: "Combine conditions with" **AND** (every condition) or **OR** (at least one), then up to 10 conditions, one row each (a column box: click it for every column with its type in a short list, type to search anywhere in the names, ↑/↓ and Enter to pick, Esc to close the list; an operator that fits the column's type; a value; a trash icon), **+ Add condition**, and Enter or Apply; an unknown column is marked and nothing runs. While a filter is on, the filter icon is blue (hover says how many conditions; a click shows and edits them) and the red clear icon beside it removes them all; with none it is greyed out. Values always go to the server as parameters. Pages follow the primary key with the server's cursor (`after`, as in [Paging](crud.md#paging)): Next and Previous only, the same speed on any page; a table without a single-column primary key shows its first page only. `LIKE`/`ILIKE` work on every column type (compared as text) and, without a `%` in the value, search for it anywhere in the value (`adm` is `%adm%`). When a `LIKE`/`ILIKE` filter that starts with `%` takes 100 ms or more, a note under the card's header explains it is a full table scan and offers the trigram index SQL that makes such searches fast (`CREATE EXTENSION IF NOT EXISTS pg_trgm;` plus a `gin_trgm_ops` index on the column).
- **Large values and wide tables**: in a table with a single-column primary key, a text, json, jsonb or xml value over 16 KB comes as a 1,000-character preview (measured in SQL, so the page stays small); the row panel, double-click, the page's CSV, editing and deleting read the whole row by its key first (editing waits until it has). A table with more than 40 columns fills only the columns in view as the grid scrolls. Any table or column name works (capitals, spaces, quotes).
- **Row Panel**: Opening a table (or a page, a filter, a refresh of it) shows its first row in a panel beside the grid, so every table has the same layout: the grid and the panel are two cards (a defined border and a soft shadow, the grid's header a grey band) on a grey backdrop; both cards have the same header band: the grid card's shows the table with the rows in view (this page, with its filter) and the table's size (`orders` / `100 rows · 244 MB`; hover for PostgreSQL's estimate of the whole table's rows, from `pg_class`, instant at any size, never a `COUNT(*)`), then on one line two groups split by a thin divider: the page size and the pages (`100 ▾ ‹ Page 1 ›`), then refresh, download, add (+), the filter icon and the clear icon; every dropdown in the page has the same chevron; a narrow card drops the "Page 1" label, and the panel never grows wider than leaves the grid card about 470 px (default 42% of the space, at most 480 px); the grid scrolls sideways when the columns don't fit and keeps a gap before the panel; a table without rows shows "No rows" there. The panel is always there for a table, view or materialized view (not for Query runner results). Click any cell in the Rows tab to show that row: a view-only table (Column, Type, Value; the Column as wide as the longest name, up to 45%; arrays as `{a,b}`), with a field filter; its header is a grey band like the grid's header: the table (`users`) with the row's key under it (`id = 52`) and a copy icon for the value. Its download icon saves the row vertically as CSV, one line per column (Column, Type, Value), after a confirmation. Clicking another cell switches the panel to that row; clicking elsewhere leaves it open. Drag the panel's left edge to widen it (remembered; double-click the edge to reset). Selecting text in the grid does not open it. ↑/↓ move to the previous or next row. The trash icon deletes the row after a confirmation (the table and key as the dialog's subtext): the row is found by its primary key, deleting is refused in read-only mode, and refused if the row changed since it was shown.
- **Field modal**: Click a field in the row panel, or double-click a cell, to open it: the column name with its type, nullable and default as subtext, and Edit and Copy icons (disabled, with the reason on hover, when they can't be used). One size for every type, in view and edit; long content scrolls inside and long lines wrap. The value is shown by its type: JSON indented and coloured, arrays as a numbered list, booleans as true/false, dates with your local time and how long ago, numbers formatted when that reads differently. Its size is in the header after the type, in one format for every field: characters (text, JSON; with the lines when there are several), items (arrays) or bytes (bytea). A query result's cell only shows its value.
- **Cell Editing**: Edit in the field modal works by type: a JSON editor (coloured, Tab indents, Format), item rows for arrays (type in a row, the trash removes it, **+ Add item** or Enter adds one, `NULL` for a null item), true/false buttons for booleans, the browser's date picker for `date` and a date-and-time picker (to the second) for timestamps, with **Now** (`timestamptz` shows and saves your local time with its offset), one line for numbers, bytea (hex) and short text, a text box otherwise. The value is checked as you type and **Save** stays disabled until it looks right and has changed; **Set NULL** and **Set default** are disabled, with the reason on hover, when the column is NOT NULL or has no default. **Save** (or ⌘/Ctrl+Enter, or Enter in a one-line field) writes it; Esc goes back to the value. The row is found by its primary key and PostgreSQL converts the value to the column's type, so a wrong format shows its error and saves nothing. Every column can be edited except the primary key and generated or identity columns; editing is off in read-only mode, for views, and for tables without a single-column primary key. `users.password` is saved as an argon2 hash by default (Atom's hasher); with the toggle off it accepts only an existing `$argon2…` hash. If the cell changed since the rows were loaded, the save is refused so nobody's change is overwritten; reload and try again.
- **Add a row**: the plus icon after the download icon (tables only, off in read-only mode) opens a compact form with the same input per type as Edit (item rows for arrays, the JSON editor, true/false, the date picker). Required columns (NOT NULL without a default) are marked `*`; an empty field is left out, so the column gets its default (shown as the placeholder) or NULL. Columns only later flows set are folded under one closed line ("N more columns set later") as name chips: the key the database numbers (locked), generated columns, and, when they may be left empty, `created_at`, `updated_at`/`updated_by_id`, `verified_*`, `deactivated_*`, `deleted_*`, `is_protected`, `last_active_at`, `read_at`, `finished_at`, the `worker_*` columns and `oidc_*` (`SET_LATER` in the page). A chip's click moves it into the form; **Later** folds it back. Insert triggers on the table are named there too. `users.password` is hashed with argon2 like an edit. **Create** stays disabled until required fields are filled and every value looks right; the new row's key shows in a message and the rows reload.
- **Downloads**: every download icon asks first, saying what the file will hold: the rows icon downloads the rows on the current page (with its filter and order; the dialog says when the table has more pages, and the Query runner's **Download** gives every row, written by PostgreSQL itself (`COPY ... TO STDOUT CSV HEADER`): arrays as `{a,b}`, booleans `t`/`f`, NULL empty and an empty string `""`), and each tab's icon downloads the rows its search and filters show.
- **Cards everywhere**: the detail tabs (Columns, Indexes, Constraints and the rest), Database info and Server health use the same grey backdrop as Rows: each tab's toolbar sits on it above its table card (grey header band), and each info or health section is a card. Dialogs have two widths: 480 px for messages and choices, 560 px for forms and values (a field, add a row, the filter).
- **Tab filters**: Columns filter by data type (the types in the table, with counts), key, nullable, default and generated; Indexes by method, unique, primary and partial; Constraints by kind, deferrable and validated. A red **Reset** appears while a filter or the search is on.

- **Server health** (pulse icon in the header, while connected): the whole server the connection is on, as far as its login may see: first the overall status (No upgrade needed, Keep an eye on it or Upgrade recommended, the current one filled, with one line saying why and what to do) and its signals (the same as Monitor's Database tab, over every database), the server (version, uptime, connections against `max_connections`, memory settings), every database's size, connections, transactions, rollbacks, cache hit, deadlocks, temp spill and XID age, connections by database and state, queries running over 5 seconds, sessions idle in a transaction over a minute, blocked queries with their blocker, and checkpoints. PostgreSQL decides what a login sees: a superuser or a member of `pg_monitor` sees every session and query; another login sees other users' sessions only as counts and shows "no access" for a database it may not open. One read-only transaction with a 20 s timeout; Refresh loads it again. Monitor stays on the project's master database; server health of any server is here, from the URL you connect with.

PgWeb's own requests are not written to `log_api` (`"is_log_api": False` on `/pgweb` in `config_api`), so browsing does not fill the API log. PgWeb can run any SQL on any database it connects to, so `/pgweb` is off by default. Set `config_is_pgweb_enabled=true` in `.env` on a developer machine only. Even then it accepts a request only when:

- it comes directly from this machine (`127.0.0.1`/`::1`), with no proxy or tunnel headers such as `X-Forwarded-For`, so `ngrok`, `cloudflared`, nginx or a sidecar cannot expose it;
- its `Origin`, if any, is Atom's own address, so other websites open in your browser cannot send it SQL;
- it is sent as `Content-Type: application/json`, which browsers cannot send cross-site without a CORS preflight.

### C. Monitor (`/page/monitor`)
One page for how the server is doing, with a tab per topic; each fact appears on one tab only, and a line under the tabs says what the tab covers and whether it is this worker or the whole server; every card has one line under its title saying what it shows and what to look for, and every number tile an ⓘ that explains it on hover or tap. Each tab loads its data when opened, and Refresh reloads it; the page remembers the last tab and choices.
- **Memory**: the RAM of the worker that answers: process and machine memory, uptime, threads and CPU time; RAM over time (read once a minute since the worker started, up to the last 24 hours, one `psutil` call; kept in the worker's memory, so a restart starts it again; a leak shows as a line that keeps rising); each item Atom keeps on `app_state` with its kind from the name prefix (`cache` safe to lose, `buffer` rows waiting to be written, `runtime` live state, `config`, `extend`; `other` means a name without a known prefix), entries and size, biggest first (sizes and counts only, never values; clients are left out, see App); the total of Python objects (a number that keeps rising between refreshes points to a leak) and the most common object types, to spot leaks; and allocation tracing: Start turns on Python's `tracemalloc` and lists the source lines holding the most memory, each marked Atom, Project or Package. It slows the worker, so it stops by itself after 5 minutes.
- **Requests**: traffic from `log_api` for the last hour, 24 hours or 7 days: totals, error rate, average and p95 response time, a requests-over-time chart, the busiest and slowest APIs, status codes and the most active users.
- **Errors**: failed requests (status 400 and above) split into server (500+) and client (400–499) errors, grouped by API and status with the last error, and the latest 50 failures. Background failures are on Background.
- **Database**: the master database, always (named once, under the page name, as host / database; a click opens a dialog with the URL's parts in a table, password as dots, then the connection string, password hidden, with a copy icon that copies it without the password. Analytics and PgWeb name theirs the same way, the host shrinking with "…" so the database always shows): the user and PostgreSQL version; pool use for every PostgreSQL connection, marking the one `log_api` writes to; and for the chosen one: size, waiting locks, queries running over 5 seconds, the biggest tables (rows, dead rows, scans, last vacuum) and the most expensive statements (needs `pg_stat_statements`). An **upgrade check** comes first: one verdict (no upgrade needed, keep an eye on it, upgrade recommended) from the server's own counters since their last reset: data size and its growth (information only: PostgreSQL can't see the disk size), connections against `max_connections`, memory (reads served from RAM), work memory (sorts and joins spilled to disk), write load (WAL written per checkpoint interval against `max_wal_size`) and deadlocks (a code issue, never an upgrade). Each signal is OK, Watch or Upgrade (Data size: Info), and an upgrade lists what to ask DevOps for (e.g. a higher `work_mem`), with a button that copies that request.
- **Background**: periodic tasks (RAM history among them), rows waiting in the write buffers, running background tasks, open websockets, and error counters. Failed queue jobs are kept in each broker's `<channel>_failed` (see the queue docs); for the queue Redis, the page shows each channel's waiting, running and failed jobs and whether a consumer holds it.
- **Redis**: every `config_redis_url_<name>`, read-only (`INFO`, `DBSIZE` and one timed `PING` from this server, 5 s timeout), one block each headed by its key name, status and URL (never the password), then its tiles: ping, memory used and peak, with its limit when the server reports one (Azure does not), keys and expired keys, hit ratio (under 80% in red), load (ops per second, clients, rejected), evicted keys with the eviction policy (`noeviction`: writes fail when memory is full), and version with uptime. One that cannot be reached shows its error; with none configured, the tab says so.
- **App**: Atom's version, Python, packages, workers, mode, routes and `func_*` functions (each split into Atom's and the project's), which clients are on, and every `config_*` setting; secrets and connection URLs only show whether they are set.

With `config_uvicorn_workers` above 1, Memory and Background describe the worker that answers, and each refresh may reach a different one; the header names it. Requests and Errors need API logging (`log_api`).

The page is independent of the other pages: it logs in itself (role 1, the page standard) and keeps one localStorage key, `monitor` = `{v, token, user, synced_at, tab, hours, connection}`, so it works on a server without the API console. Its Sync downloads the user again. It reads `GET /admin/monitor` (see 4b). Current RAM uses the `psutil` package.

### D. Analytics (`/page/analytics`)
Read-only insights for the backend's developers (role 1, the same login as every page): one click shows what the database holds and how the API is used, without writing a query. Rows, SQL and exports are PgWeb's, and changes go through PgWeb or the API page; Analytics only reads, through Atom's `/admin/*` read routes.
- **Sidebar**: the sections, one button each: **Overview** (users, API traffic and data at a glance), **Users** (sign-ups over time, users by role, the most active and the newest users), **Access** (roles in use, admins, users by permission and who holds permissions), **API traffic** (requests over time, callers, failure rate, response time, the busiest and slowest APIs, responses by status), **Errors** (failure rate, errors over time, the APIs that fail most, the most common messages, the latest errors) and **Data** (database size, the biggest and the fastest-growing tables, every table). Under the title, the master database as `host / database / public`, as PgWeb shows its connection.
- **A table**: click one in Data for its insights: rows (estimate), size, newest row, rows added today, this week and this month, new rows per day (when `created_at` is indexed), how its rows split on the columns that group well (labelled codes, yes/no, role, status, type, ...; on tables over about a million rows each breakdown reads only when clicked) and its columns in plain words (kind, required, unique, fast to filter, labels).
- **Ranges**: Overview, Users, Access, API traffic and Errors show the last 24 hours, 7 days or 30 days (one choice for all).
- **Scale**: no full count anywhere: table rows are PostgreSQL's estimate (`pg_stat_user_tables`), `users` is read once per section (grouped), `log_api` only within the range (`created_at`), and growth only on an indexed `created_at`; each query has the server's 30 s limit. `log_api` is read from the database it is written to (`config_postgres_db_log_api`); with `config_is_log_api` off its cards say so.
- **Saved views**: each section and table is saved in IndexedDB (`analytics`) and shown from there with its age ("Updated 5 min ago"); **Refresh** reads the open view again, and a Sync (every 3 hours, or from the account menu) drops them all.
- **Browser storage** (the page standard): localStorage `analytics` = `{v, token, user, synced_at, range}`; IndexedDB `analytics`: `reference` (schema, `/info`, row estimates, the server settings it uses) and `analytics` (the saved views).

## 2. Administrative APIs (`/admin/*`)

Access to `/admin/*` requires an authenticated user with **`role: 1`** (root superadmin).

### 1. Raw SQL Query Runner (`POST /admin/postgres-query-runner-read`)
Executes read SQL on master, or on another database with `?connection=<name>`:
```bash
POST /admin/postgres-query-runner-read?connection=replica1
{"sql": "SELECT count(*) FROM users;"}
```

### 2. Table Data Imports (`POST /admin/*-import`)
Bulk import data from external systems into PostgreSQL:
- **Postgres Import** (`/admin/postgres-import`): Import a CSV into any table, `users` included (form fields `mode` = `create`/`update`/`delete`, `table`, `file`; target database with `?connection=<name>`, default master). A `password` column in `users` is hashed (Argon2) on create and update.
- **MongoDB Import** (`/admin/mongodb-import`): Ingest BSON collections into structured relational tables.

### 3. Schema and Cache Refresh
- **Schema** (`GET /admin/postgres-schema`): Returns Atom's schema cache (`cache_postgres_schema_dict`) for master, or for another database with `?connection=<name>`, with no database query: tables, and per column the type, nullable, default, primary key, unique and indexes. It is what Atom checks requests against, refreshed at startup and by `/admin/sync` (see [Picking a database per request](database.md#picking-a-database-per-request-connectionname)). Any other query parameter is refused.
- **Refresh caches** (`GET /admin/sync`): Flushes the create buffer, then re-reads every schema cache, the OpenAPI spec, `cache_config` and the user role/status caches without a restart.

### 4. Background error counters
Failures that happen outside a request's response are otherwise only printed; the Monitor page's Background tab (`GET /admin/monitor?view=background`) counts them, next to the rows waiting in each write buffer:
- `log_api_write`: API log rows that could not be written (printed on the 1st failure and every 100th, so an outage does not flood the log).
- `buffer_flush`: failed buffer flushes. The rows stay in their buffer and are retried on the next flush, so a growing number means the database has been unreachable for a while.
- `buffer_dropped`: API-log rows dropped because the log buffer reached `config_buffer_rows_max` during an outage (user-data buffers reject new rows with 503 instead).
- `background_task`: failed `?is_background=true` requests.
- `cleanup`: failed in-memory cache cleanups.
- `schedule`: failed checks or starts of scheduled scripts (a script's own failure is its `script_run` row, [schedule.md](schedule.md)).

Counts are per process and reset on restart.

### 4b. Monitor (`GET /admin/monitor`)
The one route behind the Monitor page (admin only, kept out of `log_api`); helpers are in `function/monitor.py` and `function/memory.py`.
- `view`: `memory` (default), `requests`, `errors`, `database`, `background` or `app`.
- `hours`: `1`, `24` (default) or `168`, for `requests` and `errors`.
- `connection`: the PostgreSQL connection for `database` (default `master`).
- `trace`: `start` or `stop` turns allocation tracing on (for 5 minutes) or off first; use it with `view=memory`.

### 5. Slow Queries (`GET /admin/postgres-slow-queries`)
Lists this database's most expensive statements from `pg_stat_statements` (master, or `?connection=<name>`). Values in the query text are already `$1`, `$2` placeholders.

- `limit`: rows to return, `1`–`100` (default `20`).
- `order`: `total_time` (default; where the database spends its time), `mean_time` (slowest single calls) or `calls`.
- Each row has `calls`, `total_ms`, `mean_ms`, `max_ms`, `rows`, cache `shared_blks_hit`/`shared_blks_read`, the `query` and `share_pct` of all statement time in this database. `since` is when the counters were last reset.
- When the extension is not enabled the response is `{"is_enabled": false, "help": ...}` instead of an error. See [performance.md](performance.md#3-slow-queries) to enable it.

`POST /admin/postgres-slow-queries-reset` clears the counters for the current database only, so you can measure a fresh period: reset, use the app or run the load test, then read the report.
