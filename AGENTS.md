# Atom agent guide
Rules Atom enforces at import, startup, sync and CI. Follow exactly. Read by AI agents, not humans: dense on purpose.

## Work
- Work autonomously; ask only for essential missing info or destructive actions outside the request.
- Match surrounding code: naming, density, one-line statements, comments. Never expose `.env` values or credentials (key names only).
- One simple rule over exceptions; no backward-compat shims.
- Docs and readmes describe patterns (`<feature>.py`, `/page/<name>`), never specific file names, so they never go stale (the root `readme.md` may link to docs).
- This file is the only rules file, the same in every project; a project's feature details and business rules go in `docs_extend/<feature>.md`.
- A framework change keeps Atom's design decisions (the table in `docs/about.md`, with the reason for each) unless the user asks to change one.

## Ownership and sync
- Atom owns every unsuffixed path (core: `function/`, `router/`, `docs/`, `script/`, `static/`, `files/` and root files such as `config.py`, `main.py`, `sync.py`, `AGENTS.md`, `ruff.toml`, `Dockerfile`, `.dockerignore`; full list: `SYNC_FILES`/`SYNC_FOLDERS` in `sync.py`). The project owns `*_extend` paths and `config_extend.py`, which the Atom repo doesn't have (sync creates them). Shared: `.env` (project), `requirements.txt` and `.gitignore` (merged), `.github/` (per repo).
- Never edit core unless asked for a framework change: sync overwrites it and deletes other files in Atom folders. Refactors, renames, cleanups and lint fixes touch project files only; if core blocks the work, solve it in project paths or report it.
- `python3 sync.py` (Windows `py sync.py`, from a new shell outside the venv), from the Git root, after committing, with the app stopped. `--no-venv`: files only; `--no-outdated`: no PyPI lookup (CI: both); `--status`: versions only, changes nothing. New project: empty folder, `git init`, download `sync.py`, run it.
- Sync replaces core, never modifies existing `*_extend` files or `.env`, and creates whatever is missing: `*_extend` folders each with a `readme.md`, a starter `config_extend.py`, `tests_extend/__init__.py` (needed for test discovery), a commented `.env`.
- Version: `ATOM_VERSION` in `sync.py` (printed at startup, returned by `/info`), raised by hand in Atom; sync always takes Atom's latest `main` (no tags or releases).
- `requirements.txt` and `.gitignore` each have two headers: `# atom` (Atom's, reset every sync, never edit) and `# extend` (the project's, kept). `# extend` packages: pinned `==`, only what the code imports directly, no comments. Sync drops packages Atom no longer lists (a project still using one adds it to `# extend`) and `# extend` duplicates of Atom's, keeps the last repeated line, sorts, warns on unpinned lines, lists newer `# extend` versions and rebuilds `venv/` to match exactly. `.gitignore` `# atom` is deny-all plus Atom's paths: a top-level path is committed only if named `*_extend` or listed under `# extend` (`!<folder>/` and `!<folder>/**`).

## Where code goes
Name files after the feature across folders: `router_extend/<f>.py`, `function_extend/<f>.py`, `files_extend/<f>.py`, `static_extend/<f>/`, `docs_extend/<f>.md`, `tests_extend/test_<f>.py`; a big feature splits into `<f>_<part>.py` (`billing_invoices.py`), never unprefixed helper files.
1. API → `router_extend/<f>.py` (`router = APIRouter()`): read params, call one `func_*`, return; no business logic, no permission checks.
2. Logic → `function_extend/<f>.py`: `func_*`, available as `app_state.func_*`.
3. Files → `files_extend/`: shared constants and `param_specs` (import `files_extend.<module>`), JSON, prompts, templates (read by path from the project root). Read-only at runtime.
4. Web pages → `static_extend/` (see Pages).
5. Config → `config_extend.py`. Jobs → `script_extend/` (enqueue with `app_state.func_producer`; queue docs in `docs/`); a queued job runs at least once and may run twice, so it must be safe to repeat. Tests → `tests_extend/` (`unittest`, with `__init__.py`). Docs → `docs_extend/<f>.md`: short, behaviour and business rules only, no SQL or code dumps. Packages → `requirements.txt` under `# extend`.
6. Temporary and generated files (exports, scratch, downloads, compile output, logs; from routes, functions and scripts alike) → `tmp/<feature>/` (gitignored), created with `os.makedirs(..., exist_ok=True)`; never tracked folders or the system temp folder (`/tmp`, `%TEMP%`; pass `dir="tmp/<feature>"` to `tempfile`). Each feature deletes its own files when done (`config_is_tmp_reset`, default false, wipes `tmp/` at start); data that must survive goes in the database.
- Data users change at runtime (an option list edited from a page, a setting saved from the UI) lives in the database, never in a file: a deploy, `git pull` or fresh container replaces files. A setting is one row in Atom's `config` table (`key` unique, `value` jsonb; upsert with `ON CONFLICT (key) DO UPDATE`); other row-shaped data gets its own table in `config_postgres`. Files users download (templates, exports) are built in memory on request, or written to `tmp/`.
- Option lists (a page's selects and dropdowns), by who edits them. Developers: `config_options` (list or `.txt`/`.json` file in `files_extend/`), served by `/info`. Users: a table in `config_postgres`, designed by the project; reads through the feature's route or `config_table_public_read_allowed`/`config_table_private_read_allowed`; writes only through the feature's route (`config_api` role check, `realtime` mode) calling a `func_<feature>_*` that validates, with `created_by_id`/`updated_by_id` from `request.state.user`; the table goes in `config_table_my_create_blocked` so `/my/object-create` can't bypass it.
- Request path: middleware applies `config_api` → route → `func_*` → DB → `{"status": 1, "message": ...}`.

## Pages
What Atom enforces (startup or serving):
- A page is `static_extend/<name>.html` or `static_extend/<name>/index.html` (its other files inside `<name>/`): served at `/page/<name>`, listed on `/`, no route or `config_api` entry; `/` serves `config_root_html_path`. Every other file is served at `/static/<path>` only (`/static_extend/...` is not a URL); Atom's `static/` follows the same rule. Startup fails on a path in both folders or two pages with one name (ignoring case); restart after creating the folder.
- Link local files by full path (`/static/<name>/js/app.js`): Atom stamps `?v=<fingerprint>`, so no hand-kept `?v=`. Escape data from the database or other systems before `innerHTML`.

Defaults, not rules: use them unless a page has a real reason to differ (examples in `docs/page.md`); the page, its build (plain files, modules or a bundler) and its look are the project's own, since Atom shares backend only.
- One page per app; state such as a tab goes in the query (`/page/<name>?tab=<tab>`), not a sub-path.
- A page is standalone: its own login and storage, every key and database named after it (`<name>`), never general names like `token` or `user` (apps share `localhost` in development and may share a domain later).
- Storage by size and how long it lives: memory for what is on screen (gone on reload); sessionStorage for one tab's short-lived state; localStorage for small things kept across visits (login, user, choices) under one parent key holding one JSON object; IndexedDB for larger data (option lists, cached results). Live lists come from the server. Logout clears all of it.
- Keep the login alive: renew with `POST /my/token-refresh` shortly before the access token expires; when renewal is refused, show the login form with a plain sentence, never a raw token error.
- Use what Atom already has before writing a route for it: login `/auth/login-*`, renewal `/my/token-refresh`, the user `/my/profile`, password and profile changes `/my/user-update`, own-row writes `/my/object-create`/`-update`/`-delete`, settings and limits `/info` (`export_limit`, `config_options`), files `/public/blob-upload-*`, messages `/my/message-*`.
- Export: a dialog with the list's filters, a row count up to `/info` `export_limit` and Download, calling the feature's `/<feature>/export` (backed by `func_<db>_export`); the file is read as a stream to show progress, with no count first.
- Speed: calls that don't need each other's result go out together (`Promise.all`); only a call that needs an earlier result waits.
- Screens: a search looks in one picked column and runs on Enter or its button, not on each keystroke; one date format per page; names and titles shown in full; a link to one item opens only that item, the rest loads after.
- A long file (300+ lines) marks its sections (`/* ==== <name> ==== */` in CSS and JS, `<!-- ==== <name> ==== -->` in HTML) so `grep -n '==== '` lists them.

## Reuse Atom (search `function/` for a `func_*` before writing a helper, client or pool)
- Databases, any number per type: `.env` lines `config_<db>_url_<name>=<url>` (`<db>`: `postgres`, `mssql`, `redis`, `clickhouse`; e.g. `config_postgres_url_master`, `config_mssql_url_erp`) fill `config_<db>_url_dict`; Atom opens one pool each at startup and closes it at shutdown: `app_state.client_<db>_dict["<name>"]` (default `master`; `func_mssql_client_read` and `func_clickhouse_client_read` 400 on an unknown name). A new database is a new `.env` line, never code. A route letting the caller pick one names the param `connection` (query or body, default `master`, unknown 404), never `postgres`, `mssql`, `clickhouse` or `database`. On the admin query runners only role 1 picks it: a project that opens one to other roles gives them `master` only (403 otherwise), so its other logins stay with admins.
- Other clients, opened at startup and closed at shutdown: `client_mongodb`, `client_s3`, `client_ses`, `client_sns`, `client_openai`, `client_gemini`, `client_http` (shared HTTP session), `client_azure_blob`/`_email`/`_sms`, `client_msgraph`, `client_sftp`, queue producers. App code never opens its own pool, connection or SDK client (pool sizes: `config_postgres_pool_*`, `config_mssql_pool_*` in `.env`, one database's with a `_<name>` suffix such as `config_postgres_pool_max_size_test`; anything else is a framework change, never a second pool). Scripts open their own with `func_client_*` or the driver, reading URLs from `.env` by key.
- Helpers: params `func_request_param_read`; errors `func_api_error`; rows `func_check_table_permission`, `func_postgres_create/read/update/delete`; SQL `func_postgres_query_runner_read`, `func_mssql_client_read`, `func_mssql_query_runner_read`, `func_clickhouse_query_runner_read`; CSV `func_postgres_export`, `func_mssql_export`, `func_clickhouse_export`, `func_postgres_read_export`, `func_csv_response`, `func_postgres_import`; files `func_blob_upload_file`, `func_blob_upload_url`, `func_blob_delete_all`; email and SMS `func_email_send`, `func_otp_send_email`/`_mobile`; jobs `func_producer`, `func_run_broker`, `func_background_run`; one-worker sections `func_postgres_advisory_lock`.
- Exports: every CSV download, Atom's and a project's, goes through `func_<db>_export` (`postgres`, `mssql`, `clickhouse`; a new database type gets its own in Atom first): one read query, read with a cursor and streamed, at most `config_export_limit` rows (the only row limit, in `config.py`; a user may ask for fewer with `limit`, more is a 400; pages read the maximum from `/info` `export_limit`), returned with `func_csv_response`. A project keeps its own export route (`/<feature>/export`, its params and checks, passing an optional `limit` through); behind it, it writes only its query (filters, permissions), then calls Atom's function: never its own CSV streaming, row limit or count before the download. An export is the data as stored: the header is the query's real column names (a join names a clashing column `"<table>.<column>"`), values as they are, never renamed or relabelled (codes stay codes, ids stay ids).
- Users: `/admin/user-create` (role, username, password), `/admin/user-update`, `/admin/user-delete`, `/my/user-update`, `/my/user-delete`; read with `/my/profile` and `/admin/object-read`. The generic object APIs refuse `table=users`; never write a project user create, update, password, email or delete API (add columns to `users`, see Settings). Every `users` column is updatable unless listed in `config_column_users_my_blocked` (admins only) or `config_column_users_blocked` (nobody, through the APIs).
- Missing in Atom: write a project `func_<feature>_*` (never a `func_<atom_area>_*` name such as `func_mssql_*`, which a later Atom may add) or ask for a framework change.

## Settings
- Every `config_*` from `config.py`, then `config_extend.py`, then `.env`/environment (wins) ends up on `app_state.config_*`; new names work too. Env values are typed by the existing default (else true/false, int, JSON, string); lists become tuples.
- `.env`: secrets, URLs, machine flags; one `config_x=value` per line, no quotes, comments on their own lines (`docker --env-file` keeps quotes and inline comments in values). Developer machines: `config_is_prod=false`; `config_is_pgweb_enabled=true` only there.
- `.env` order: `# atom` (Atom's keys the backend uses), `# extend` (the project's keys the backend uses), then one `# script.<name>` per `script_extend/` script (file name without `.py`) listing every key it reads, with Atom's plain names, so that section alone runs it elsewhere. `# atom` and `# extend` are active; script sections are fully commented out and uncommented where the script runs (backend and scripts load the same file: an active copy overrides a backend key, an active `config_<db>_url_<name>` opens a backend pool).
- `config_extend.py`: `# base` (`from config import config_x as base_config_x`; a base import named `config_*` fails startup), `# atom` (Atom's dicts extended), `# misc` (overrides of plain `config_*`, e.g. `config_table_*_read_allowed`). Define each `config_*` once. Project limits and constants are not config: function default parameters or `files_extend/`; browser-only values (cache hours) in the page JS.
- Extend, never replace: `config_x = {**base_config_x, "key": value}`, spread at the top level only; to change one of Atom's keys write its whole value (never `**base_config_x[key]`). `config_postgres`: `{**base_config_postgres, "table": {**base_config_postgres["table"], "<table>": [...]}}`; columns added to an Atom table: `[*base_config_postgres["table"]["<atom_table>"], {...}]`, never `.append`.
- Startup fails if `config_extend.py` drops Atom's entries from `config_api` (routes), `config_postgres` (`extension`, `table`, `control`, `sql` and their entries) or `config_column_int_mapping` (codes); values and labels may change, additions are free.
- New tables: column spec in Atom's extend docs in `docs/`; owner columns get `"index": "btree(created_by_id,id)"`.

## config_api (the middleware enforces it before the route; never re-check in a route)
- Every route needs an entry with a unique `id` (200+ for project routes) and `is_token`; startup fails on a missing entry, an entry without a route, a repeated `id` or a project route under 200.
- `is_token: True` → access token required (401); `user_check_*` need it too, and every such route has a `user_check_role` whose roles include 1.
- `user_check_role: {"mode": m, "roles": [..]}` (403); `user_check_deactivated`/`user_check_deleted: {"mode": m}`. `m`: `token` (fastest, stale until re-login), `redis` (cached), `realtime` (DB each request; admin and destructive routes), `inmemory` (startup snapshot, single worker).
- Roles: 1 is Atom's admin (every `/admin/*` route); project users start at 2 (one kind of user: role 2, routes allow `[1, 2]`); each new kind takes the next number and is added only to the routes it may call. Label every role used in `config_column_int_mapping["users"]["role"]`; who may log in: `config_login_allowed_roles` (`config_signup_allowed_roles` for self sign-up).
- Tables written only through feature routes go in `config_table_my_create_blocked`. An `is_token: False` route that writes data checks a shared secret from `.env` in its function; never re-enable an Atom route that ships `is_active: False`.
- `rate_limit: {"mode": "redis"|"inmemory", "limit": N, "window_sec": S}` (429); `cache: {"mode": "redis"|"inmemory", "ttl_sec": S, "is_per_user": bool}`; `is_connection_param: True` allows `?connection=<name>`; `is_active: False` → 404; `is_log_api: False` keeps requests out of `log_api`.
- WebSocket entries take only `id` and `is_active`; the socket function checks both and authenticates itself (token as first message).
- `request.state.user` = decoded token (`config_column_token_encode` columns) or `{}`; user id and role come only from it, never from params. Row ownership and other rules `config_api` can't express go in a `func_*`.

## Routes and functions
- Path (a default, not a rule): `/<feature>/<action>`, the action a verb last: `read`, `read-single`, `create`, `update`, `delete`, `export`, `<thing>-read` (`/finance/dashboard-read`, `/application/filter-option-read`); `my-<action>` for the caller's own rows (`/application/my-create`). One route per screen task, not one per chart, and no `?kind=` switch between unrelated reads. Another style is fine where it reads better (a domain verb such as `/mdm/close`, an outside system's name); keep one style within a project.
- A page may write through Atom's `/my/object-create`, `/my/object-update` and `/my/object-delete`: the database enforces ownership (`created_by_id`, or a column listed in `config_column_ownership_*`). Write a feature route only when a write needs more than ownership (validation, several tables, a rule about who may change what).
- Route: `async def func_api_<area>_<name>(*, request: Request):`, then `app_state = request.app.state`; use only `app_state.func_*/config_*/client_*`, `request.state.client_postgres`, `request.state.cache_postgres_schema`; never import from `function`.
- Params only via `await app_state.func_request_param_read(request=request, mode="query"|"body"|"form"|"header", param_specs=[...])` (shared specs in `files_extend/<f>.py`); add `strict=True, strict_types=True, reject_unknown=True` to refuse unknown or mistyped params (recommended). Spec keys: `name`, `type` (`str`, `int`, `float`, `bool`, `list`, `list:int`, `dict`, `file`, `any`), `required`, `default`, `allowed`, `minimum`, `maximum`, `min_length`, `max_length`; with `is_connection_param` add `{"name": "connection", "type": "str"}`. Never declare the middleware flags `is_disable_cache` and `is_background`.
- Return `{"status": 1, "message": result}`; errors `raise app_state.func_api_error(message=..., status_code=...)` (plain `Exception` → 400). List routes with `app_state.func_app_route_list(app=request.app)`.
- Functions: `func_*`, keyword-only, unique across `function/` and `function_extend/` (duplicates fail at import); `_*.py` and subfolders are not loaded; import from defining modules (`from function.request import ...`). `function_extend/<f>.py` defines only `func_<f>_*` (helpers shared across features: `<project>.py`, `func_<project>_*`).
- Who may see a row and who may change it come from one shared helper, and a caller's own filter never removes an owner restriction; cast ids and codes from request bodies before comparing.
- `app_state` names say what they hold: `func_`, `config_`, `client_`, `cache_` (kept for reuse, safe to lose), `buffer_` (rows waiting to be written), `runtime_` (tasks, locks, counters). A project adds none: its data goes in `app_state.extend`.
- Optional `func_extend(*, app_state)` runs once after Atom's clients are ready (its return is `app_state.extend`); `func_extend_shutdown(*, app_state)` runs before they close: open and close project clients and pools there (never leave a pool unclosed). Never edit `main.py` for this.

## Data and security
- Rows only through `func_check_table_permission` and `func_postgres_create/read/update/delete` (inside a feature's transaction too: pass its `client_postgres_conn`), not hand-written `INSERT`/`UPDATE`/`DELETE` or plain `SELECT`: they check columns, types and ownership (`created_by_id`; CRUD and ownership docs in `docs/`) in one round trip. Hand-written SQL only for what they can't express (joins, aggregates, row locks). Never `is_trusted=True` with request data.
- SQL values bound as `$1, $2`, never in f-strings; identifiers only after `^[a-zA-Z_][a-zA-Z0-9_]*$` or an allow-list, quoted. Postgres only through asyncpg (`app_state.client_postgres_dict[...]` in the app, `func_client_postgres` or `asyncpg` in scripts; no psycopg or SQLAlchemy); reg* types: `$1::text::regclass`, `to_regclass(x) IS NOT NULL`. Redis names `api_response`, `user_state`, `ratelimiter`, `queue` are Atom's.
- Speed: a list returns `has_next_page` (fetch limit + 1), never a total `count(*)`; page after the last row (`WHERE id < $1 ORDER BY id DESC LIMIT n`, as `func_postgres_read(after_id=...)` and the `object-read` routes' `after_id`/`next_after_id`; a custom sort uses a cursor of its sort column and `id`), never a growing `OFFSET`, with an index matching each list's filter and sort (`docs/crud.md`); read what a request needs in one query (one row for several checks, `= ANY($1)` for ids, many rows updated with one `UPDATE ... FROM unnest(...)`), not one query per check or item; work out what depends only on a column or type once, before the row loop; a transaction only around statements that must succeed together.
- Pool connections go back without a session reset: never change session state in project code (no plain `SET`, `set_config(..., false)`, `LISTEN` or unreleased advisory lock); use `SET LOCAL` inside a transaction, and run SQL someone typed through `func_postgres_acquire_clean`.
- Responses over 1 KB are gzipped by Atom when the client accepts it: never compress in a route or add compression middleware; a route sending bytes it already compressed sets `Content-Encoding`. Measured numbers: `docs/performance.md`.
- Request bodies over `config_request_body_max_kb` (10 MB; multipart `config_request_form_max_kb`, 100 MB) get 413 before they are read: a project needing more raises the setting in `config_extend.py`, never reads around it; bigger files go straight to storage with a presigned upload.
- Production: `config_token_secret_key` 32+ bytes. With `config_uvicorn_workers` > 1: no `inmemory` mode for caches, rate limits or user checks, and `/my/message-socket` stays inactive (startup fails).
- Never fill missing business data with placeholders (names, dates, codes, branches) or ship demo data: leave it empty and say so. Deploy settings (Bicep, workflows, App Service) set only `config_*` keys that Atom or `config_extend.py` reads.

## Style
- Atom's own files (core): headers, lowercase singular, no module docstrings (routers `# import`/`# router`/`# api`; functions `# import`/`# function`); one name per import line (`from x import a`, then `from x import b`). Project files follow the project's own style, except scripts (below).
- Scripts (and `sync.py`): `# command: <how to run>` (first line; one line per way to run), `# info: <one line>` (optionally followed by short `# - step` bullet lines), then `# import` (packages, then project code: `config`, `config_extend`, `files*`, `function*`; a setting with a default in code comes from here, `from config import config_column_regex`), `# config` (only what differs per machine, read only here: `load_dotenv(".env")`, then one `name = os.getenv("<exact .env key>")` per value: URLs, keys, passwords, any `config_*` whose default is `None`; nothing else), `# setting` (hard-coded values, UPPER_CASE), `# logic` (helpers, then `main()`), `# main` (only `if __name__ == "__main__":` calling `main()`). Every section present, even empty; one blank line before each header (`# info` and every section; the `# command` lines stay together); no blank lines inside `# config`/`# setting`.
- A script imports only packages in `requirements.txt` and sets its exit code with `sys.exit(...)` inside `main()`. Tests write temporary files only under `tmp/` and build project tables with `func_postgres_schema_init` from `config_postgres`.
- Atom's `script/` `# logic`: one top-level helper per named step (`noun_verb`: `task_claim`, `batch_fetch`), keyword-only, getting `# config` values as arguments (`# setting` constants may be read directly); `main()` is last, at most 30 lines, defines no functions, reads like steps (read config, open clients, call helpers, close in `finally`); async scripts keep `main()` sync and call `asyncio.run(...)` once. CLI flags and process state (`sys.argv`, argparse, `os.environ.copy()`) are read in `# logic`: an `args_read()` helper or `main()`. Exception: `func_run_broker` callbacks take its positional arguments.
- A `script_extend/` script needs only the sections above; how its `# logic` is organised is the developer's choice.
- Atom's `script/` holds only scripts that work in every project: imports are stdlib, packages, `config` and `function` (never `files`, `router` or `*_extend`; `sync.py` stdlib only); outside values are read only in `# config`; writes go only to `tmp/`. Scripts tied to a project's tables go in `script_extend/`.
- A `script_extend/` script is one `.py` file per job; it may import stdlib, packages, `config`, `function` and the project's own `function_extend`/`files_extend` (move helpers there when a script grows); outside values only from `config.py` or the environment, in `# config`; runtime data and resume state in `tmp/<script>/`, kept while a run can resume and deleted once it succeeds.

## Verify
- `venv/bin/python -m script.check`: Atom's startup checks (config, duplicate `func_*`, secrets, imports; no connection opened, no server started), ruff, a syntax check of every page's JavaScript and every test in one run, the same command CI runs; a summary line, then only failures and skip reasons; a test name such as `tests_extend.test_invoice` runs just that. Start the app only to check database connections. Windows: `venv\Scripts\` instead of `venv/bin/`.
- Database tests: a throwaway local database, dropped afterwards; never a shared or production one.
- Keep tests light: the whole check runs in seconds. No heavy tests for a script's run (resume, retries, downloads, prompts, publishing, long runs): its bugs show in the terminal when it runs. Test only a rule whose mistake gives wrong data without an error (matching, classification, a filter's SQL).
