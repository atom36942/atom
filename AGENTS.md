# Atom agent guide
Rules Atom enforces at import, startup, sync and CI. Follow exactly. Read by AI agents, not humans: dense on purpose.

## Work
- Work autonomously; ask only for essential missing info or destructive actions outside the request.
- Match surrounding code: naming, density, one-line statements, comments. Never expose `.env` or credentials (key names only, never values).
- Prefer one simple rule over exceptions; no backward-compat shims.
- Docs, readmes and AGENTS.md describe rules and patterns (`<feature>.py`, `/page/<name>`), never specific file names, so adding, moving or renaming a file never makes them stale (the root `readme.md` may link to docs).

## Ownership
- Atom owns every unsuffixed path; the project owns `<name>_extend` (`router_extend/`, `function_extend/`, `files_extend/`, `static_extend/`, `script_extend/`, `tests_extend/`, `docs_extend/`, `config_extend.py`). Shared: `.env` (project), `requirements.txt` and `.gitignore` (merged), `.github/` (per repo).
- Never edit core (`function/`, `router/`, `docs/`, `script/`, `static/`, `files/`, `config.py`, `main.py`, `sync.py`, `AGENTS.md`, `ruff.toml`, `.gitignore` above `# extend`, `.dockerignore`, `Dockerfile`, `readme.md`; full list: `SYNC_FILES`/`SYNC_FOLDERS` in `sync.py`) unless asked for a framework change: sync overwrites them and deletes other files in Atom folders. Refactors, renames, cleanups and lint fixes touch project files only; if core blocks the work, solve it in project paths or report it.
- `.gitignore` is shared and ignores unlisted paths: sync resets Atom's allow-list above `# extend` and keeps the project's lines under it. Top-level paths are committed only if named `*_extend` or listed under `# extend` (`!<folder>/` and `!<folder>/**`).
- The Atom repo has no `config_extend.py` or `*_extend` paths: sync creates them in each project.

## Sync
- `python3 sync.py` (Windows `py sync.py`, from a new shell outside the venv), from the Git root, after committing, with the app stopped. Flags: `--no-venv` (files only), `--no-outdated` (skip the PyPI lookup); in CI, use both. `--status` shows the project's Atom version and the latest, changing nothing. New project: empty folder, `git init`, download `sync.py`, run it.
- Replaces core files; never modifies existing `*_extend` files or `.env`; creates each one whenever it is missing: `*_extend` folders, a `readme.md` in each, starter `config_extend.py`, `tests_extend/__init__.py` (needed for test discovery), commented `.env`.
- Atom's version is `ATOM_VERSION` in `sync.py` (also printed at startup and returned by `/info`): sync always takes Atom's latest `main` (no tags or releases), and the number is raised by hand in Atom.
- `requirements.txt`: only two headers, `# atom` (reset to Atom's list every sync; never edit) and `# extend` (project packages, pinned `==`, only packages the code imports directly, no comments). Sync drops packages Atom no longer lists from `# atom` (a project that still uses one adds it to `# extend`), drops `# extend` duplicates of Atom packages, keeps the last of repeated lines, sorts, warns on unpinned lines and lists newer `# extend` versions. Rebuilds `venv/` to match exactly, so Atom's upgrades apply.

## Where code goes
Name files after their feature across folders: `router_extend/<f>.py`, `function_extend/<f>.py`, `files_extend/<f>.py`, `static_extend/<f>/`, `docs_extend/<f>.md`, `tests_extend/test_<f>.py`; a big feature may split into `<f>_<part>.py` (`billing_invoices.py`), never unprefixed helper files.
1. API → `router_extend/<feature>.py` (`router = APIRouter()`): read params, call one `func_*`, return; no business logic, no permission checks.
2. Logic → `function_extend/<feature>.py`: `func_*`, available as `app_state.func_*`.
3. Files → `files_extend/`: shared constants and `param_specs` (import `files_extend.<module>`), JSON, prompts, templates (read by path from the project root). Read-only at runtime: never write to it (runtime data → database, generated files → `tmp/`).
4. Web pages → `static_extend/`, served at `/static/<path>` together with Atom's `static/` (same path in both, or two pages with one name such as `<name>.html` and `<name>/index.html`, stops startup; names compare ignoring case, hidden OS files such as `.DS_Store` are ignored; `/static_extend/...` is not a URL; restart after creating the folder). A page is standalone: its own login and its own browser storage, named after the app: one `localStorage` key `<app>` holding a JSON object of small values (token, user, UI choices such as tab, year, sidebar), never general keys like `token` or `user`; this holds for every app, even one that has a domain to itself: during development all projects share `localhost`, and apps may later share a domain; big data (cached query results, option lists, rows) goes in IndexedDB database `<app>`, a disposable cache: raise its version to empty it, never convert old entries; `sessionStorage` as the page needs it, under the same one key `<app>`. Page JavaScript is plain files the browser loads as written, no bundler, build step or generated files in git; a page that outgrows one script becomes ES modules loaded from `/static/<app>/js/app.js`, wired with `addEventListener` (no inline `onclick` handlers).
   - New app: `static_extend/<app>/index.html` with its assets inside `<app>/` (`css/`, `js/`, `files/`), linked absolutely (`/static/<app>/js/app.js`, never `js/app.js`), or one file `static_extend/<app>.html`; use lowercase names (`[a-z0-9_-]`) for clean URLs; no base64-embedded images. It opens at `/page/<app>` and is listed on `/` automatically (no route or `config_api` entry): name = file or folder name, first letter capital. `/` serves the page in `config_root_html_path`.
   - One page per app, no nested routes or sub-path pages: state such as a tab goes in the query (`/page/<app>?tab=<tab>`), read by the page's JS. One rule: every top-level `<name>.html` and `<name>/index.html` in `static/` or `static_extend/` is a page (Atom's own too), whatever the name, listed on `/` and served at `/page/<name>`; nothing else is (other files, deeper pages such as `<app>/<sub>/index.html`, folders without `index.html`), all still served at `/static/...`. Its API routes follow 1–2.
   - A page that logs in keeps the login alive on its own: on open, when its tab comes back into view, every minute and before each request, it reads the access token's `exp` from the token itself; with under 5 minutes left it gets new tokens from `POST /my/token-refresh` (refresh token as Bearer) and saves them; when the refresh token has expired or is refused (401/403) it clears the login and shows the login form with "Your login has expired. Please log in again."; a network failure keeps the token and tries again later. Users never see raw token errors such as "Signature has expired".
5. Config → `config_extend.py` (Settings). Jobs → `script_extend/` (enqueue with `app_state.func_producer`; queue docs in `docs/`). Tests → `tests_extend/` (`unittest`, with `__init__.py`). Docs → `docs_extend/<feature>.md`: short, behaviour and business rules only, no SQL or code dumps. Packages → `requirements.txt` under `# extend`.
- Data users can change at runtime (an option list edited from a page, a setting saved from the UI) lives in the database, never in a file: tracked files are code, and a deploy, `git pull` or a fresh container silently replaces what users saved. A setting is one row in Atom's `config` table (`key` unique, `value` jsonb: upsert with `INSERT ... ON CONFLICT (key) DO UPDATE`); other row-shaped data gets its own table in `config_postgres`. Files users download (templates, exports) are built in memory on request, or written to `tmp/`.
- Option lists (what a page shows in a select or dropdown), one rule by who edits the list:
  - Developers (changed in code): `config_options` (list or `.txt`/`.json` file in `files_extend/`), served by `/info`.
  - Users (changed from a page): a `<prefix>_options` table in `config_postgres` (any prefix, usually the feature: `order_options`), one row per option: `id`, `created_at`, `created_by_id` (`btree(created_by_id,id)`), `updated_at`, `updated_by_id`, `type` (mandatory, `btree(type)`: which list, e.g. `carrier`), `value` (mandatory, the label), `code` (optional key), `is_active` (default true; hide instead of delete). One table holds any number of lists, told apart by `type`; type names are constants in `files_extend/<feature>.py`. Developers add starting options as rows (insert them, or a code default that applies until the first save); users add, edit and hide them from the page.
  - Reads: the feature's own route, or add the table to `config_table_public_read_allowed`/`config_table_private_read_allowed` when the page reads it generically. Writes: only through the feature's own route (`config_api` role check, `realtime` mode) calling a `func_<feature>_*` that validates and saves a whole list in one transaction (replace that `type`'s rows), with `created_by_id`/`updated_by_id` from `request.state.user`; add the table to `config_table_my_create_blocked` so `/my/object-create` can't bypass it. Code defaults (a constant) apply only until the first save.
- Temporary and generated files (exports, scratch, downloads, compile output, logs), from routes, functions and scripts alike → `tmp/<feature>/` in the project root (gitignored), created with `os.makedirs(..., exist_ok=True)`; never tracked folders or the system temp folder (`/tmp`, `%TEMP%`): Python's `tempfile` uses it by default, so always pass `dir="tmp/<feature>"`; each feature deletes its own files when done (`config_is_tmp_reset`, default false, wipes `tmp/` at app start); keep data that must survive in the database.
- Request path: middleware applies `config_api` → route → `func_*` → DB → `{"status": 1, "message": ...}`.

## Reuse Atom (search `function/` for a `func_*` before writing a helper, client or pool)
- Databases, any number per type: `config.py` has `config_postgres_url_dict`, `config_mssql_url_dict`, `config_redis_url_dict` and `config_clickhouse_url_dict`, filled from `.env` lines `config_<db>_url_<name>=<url>` (`config_postgres_url_master`, `config_postgres_url_reports`, `config_mssql_url_master`, `config_mssql_url_erp`, ...). For each entry Atom opens one pool at startup and closes it at shutdown: `app_state.client_postgres_dict["<name>"]`, `client_mssql_dict["<name>"]`, `client_redis_dict["<name>"]`, `client_clickhouse_dict["<name>"]` (`master` is the default; `func_mssql_client_read` and `func_clickhouse_client_read` also 400 on an unknown name). A new database is a new `.env` line, never new code; scripts read the same `config_<db>_url_dict` from `config`. A route that lets the caller pick one names the param `connection` (query or body, default `master`, unknown name 404), whatever the client: never `postgres`, `mssql`, `clickhouse` or `database`.
- Other clients, created at startup and closed at shutdown: `client_mongodb`, `client_s3`, `client_ses`, `client_sns`, `client_openai`, `client_gemini`, `client_http` (shared HTTP session), `client_azure_blob`/`_email`/`_sms`, `client_msgraph`, `client_sftp`, queue producers. App code never opens its own pool, connection or SDK client (pool sizes: `config_postgres_pool_*`, `config_mssql_pool_*` in `.env`; other settings that don't fit are a framework change, never a second pool); scripts open their own with `func_client_*` or the driver directly.
- Requests and errors: `func_request_param_read`, `func_api_error`. Access rules: `config_api` (token, roles, rate limit, cache). Rows: `func_check_table_permission`, `func_postgres_create/read/update/delete`. SQL: `func_postgres_query_runner_read`, `func_mssql_client_read`, `func_mssql_query_runner_read`, `func_clickhouse_query_runner_read`.
- Users: `/admin/user-create` (role, username, password), `/admin/user-update`, `/admin/user-delete`, `/my/user-update`, `/my/user-delete`; read with `/my/profile` and `/admin/object-read`. The generic object APIs refuse `table=users`; a project never writes its own user create, update, password, email or delete API (add project columns to `users` instead, see Settings). Every `users` column is updatable unless listed: a new column only admins may update goes in `config_column_users_my_blocked`, one nobody may update through the APIs in `config_column_users_blocked`.
- CSV out and in: `func_postgres_read_export`, `func_*_query_runner_read_export`, `func_csv_cell`, `func_postgres_import`. Files: `func_blob_upload_file`, `func_blob_upload_url`, `func_blob_delete_all`. Email and SMS: `func_email_send`, `func_otp_send_email`/`_mobile`. Jobs: `func_producer`, `func_run_broker`, `func_background_run`; one-worker sections: `func_postgres_advisory_lock`.
- Option lists: `config_options` (lists or `.txt`/`.json` files, served by `/info`). Pages: `static_extend/` (Where code goes 4). Scratch files: `tmp/<feature>/`. Missing in Atom: write a project `func_<feature>_*` (never a `func_<atom_area>_*` name such as `func_mssql_*`, which a later Atom version may add) or ask for a framework change.

## Settings
- Every `config_*` from `config.py`, then `config_extend.py`, then `.env`/environment (wins), ends up on `app_state.config_*`; new names work too. Env values are typed by the existing default (else true/false, int, JSON, string); lists become tuples. `config_<db>_url_<name>` fills `config_<db>_url_dict[name]`.
- `.env`: secrets, URLs, machine flags; one `config_x=value` per line, no quotes, comments on their own lines (`docker --env-file` keeps quotes and inline comments in values). Developer machines: `config_is_prod=false`; `config_is_pgweb_enabled=true` only there.
- `config_extend.py` layout: `# base` (`from config import config_x as base_config_x`), `# atom` (Atom's dicts extended), `# misc` (overrides of Atom's plain `config_*`, e.g. `config_table_*_read_allowed`). Define each `config_*` once; never name a base import `config_*` (startup fails). Project limits and constants are not config: function default parameters or `files_extend/`; browser-only values (cache hours) live in the page JS.
- Extend, never replace: `config_x = {**base_config_x, "key": value}`; spread only at the top level; to change one of Atom's keys write its whole value (never `**base_config_x[key]`). Exception, `config_postgres`: `{**base_config_postgres, "table": {**base_config_postgres["table"], "<table>": [...]}}`; add columns to an Atom table with a new list (`[*base_config_postgres["table"]["<atom_table>"], {...}]`), never `.append` to Atom's.
- Startup fails if `config_extend.py` drops Atom's entries from `config_api` (routes), `config_postgres` (`extension`, `table`, `control`, `sql` and their entries) or `config_column_int_mapping` (codes); values and labels may change, additions are free. Atom's entries are read from `config.py` at startup.
- New tables: column spec in Atom's extend docs in `docs/`; owner columns get `"index": "btree(created_by_id,id)"`.

## config_api (enforced by the middleware before the route; never re-check in a route)
- Every route needs an entry with a unique `id` (200+ for project routes) and `is_token`; startup fails on a missing entry, an entry without a route, a repeated `id`, or a project route under 200.
- `is_token: True` → access token required (401); `user_check_*` need it too.
- `user_check_role: {"mode": m, "roles": [..]}` (403); `user_check_deactivated`/`user_check_deleted: {"mode": m}`. `m`: `token` (fastest, stale until re-login), `redis` (cached), `realtime` (DB each request; admin and destructive routes), `inmemory` (startup snapshot, single worker).
- `rate_limit: {"mode": "redis"|"inmemory", "limit": N, "window_sec": S}` (429); `cache: {"mode": "redis"|"inmemory", "ttl_sec": S, "is_per_user": bool}`.
- `is_connection_param: True` allows `?connection=<name>`; `is_active: False` → 404; `is_log_api: False` keeps requests out of `log_api`.
- WebSocket entries take only `id` and `is_active`; the socket function checks both and authenticates itself (token as first message).
- `request.state.user` = decoded token (`config_column_token_encode` columns) or `{}`; take user id and role only from it, never from params. Row ownership and other rules `config_api` can't express go in a `func_*`.

## Routes
- `async def func_api_<area>_<name>(*, request: Request):`, then `app_state = request.app.state`; use only `app_state.func_*/config_*/client_*`, `request.state.client_postgres`, `request.state.cache_postgres_schema`; never import from `function`.
- A route that takes params reads them only via `await app_state.func_request_param_read(request=request, mode="query"|"body"|"form"|"header", param_specs=[...])` (specs from `files_extend/<feature>.py` when shared); add `strict=True, strict_types=True, reject_unknown=True` to refuse unknown or mistyped params (recommended). Spec keys: `name`, `type` (`str`, `int`, `float`, `bool`, `list`, `list:int`, `dict`, `file`, `any`), `required`, `default`, `allowed`, `minimum`, `maximum`, `min_length`, `max_length`; with `is_connection_param` add `{"name": "connection", "type": "str"}`. The middleware flags `is_disable_cache` and `is_background` are never passed to routes: never declare them.
- Return `{"status": 1, "message": result}`; errors `raise app_state.func_api_error(message=..., status_code=...)` (plain `Exception` → 400). List routes with `app_state.func_app_route_list(app=request.app)`.

## Functions
- `func_*`, keyword-only, unique across `function/` and `function_extend/` (duplicates fail at import). `_*.py` and subfolders are not loaded; import from defining modules (`from function.request import ...`).
- `app_state` names say what they hold: `func_`, `config_`, `client_`, `cache_` (kept for reuse, safe to lose), `buffer_` (rows waiting to be written), `runtime_` (live state: tasks, locks, counters). A project adds none of its own: its data goes in `app_state.extend`.
- Optional `func_extend(*, app_state)` runs once after Atom's clients are ready (its return is `app_state.extend`); `func_extend_shutdown(*, app_state)` runs before they close: open and close project clients and pools there (never leave a pool unclosed). Never edit `main.py` for this.

## Data and security
- Tables via `func_check_table_permission` and `func_postgres_create/read/update/delete`; ownership via `created_by_id` (CRUD and ownership docs in `docs/`). Never `is_trusted=True` with request data.
- SQL values as `$1, $2`, never in f-strings; identifiers only after `^[a-zA-Z_][a-zA-Z0-9_]*$` or an allow-list, quoted.
- Clients: see Reuse Atom (default name `master`). Redis names `api_response`, `user_state`, `ratelimiter`, `queue` are Atom's.
- Postgres only through asyncpg, Atom's driver: `app_state.client_postgres_dict[...]` in the app, `func_client_postgres` or `asyncpg` in scripts; no other Postgres driver (psycopg, SQLAlchemy). Quote identifiers yourself (asyncpg has no SQL builder) and bind values as `$1, $2`; reg* types: `$1::text::regclass`, `to_regclass(x) IS NOT NULL`.
- Production: `config_token_secret_key` 32+ bytes. With `config_uvicorn_workers` > 1, no `inmemory` mode for caches, rate limits or user checks, and `/my/message-socket` stays inactive (startup fails).

## Style
- Headers, lowercase singular, no module docstrings: routers `# import`/`# router`/`# api`; functions `# import`/`# function`.
- One name per import line, everywhere (`from x import a`, then `from x import b`; never `from x import a, b` or `import a, b`).
- Scripts (and `sync.py`): `# command: <how to run>` (first line; one line per way to run), `# info: <one line>` (optionally followed by short `# - step` bullet lines), then `# import`, `# config` (every outside value, read only here: settings and connection URLs from `config.py` (`from config import ...`; each database picked by name, `postgres_url_reports = config_postgres_url_dict.get("reports")`), or straight from the environment with `os.getenv("NAME", default)` (importing `config` has already loaded `.env`; a script that doesn't may call `load_dotenv()`); nothing else), `# setting` (hard-coded values, UPPER_CASE), `# logic` (helpers, then `main()`), `# main` (only `if __name__ == "__main__":` calling `main()`). Every section present, even empty; one blank line before each header (`# info` and every section; the `# command` lines stay together); no blank lines inside `# config`/`# setting`.
- Atom's `script/` `# logic`: one top-level helper per named step (`noun_verb`: `task_claim`, `batch_fetch`), keyword-only, getting `# config` values as arguments (`# setting` constants may be read directly); `main()` is last, at most 30 lines, defines no functions, reads like steps (read config, open clients, call helpers, close in `finally`); async scripts keep `main()` sync and call `asyncio.run(...)` once. CLI flags and process state (`sys.argv`, argparse, `os.environ.copy()`) are read in `# logic`: an `args_read()` helper or `main()`. Exception: `func_run_broker` callbacks take its positional arguments.
- A `script_extend/` script needs only the sections above; how its `# logic` is organised is the developer's choice.
- Atom's `script/` holds only scripts that work in every project: imports are stdlib, packages, `config` and `function` (never `files`, `router` or `*_extend`; `sync.py` stdlib only); outside values are read only in `# config`; writes go only to `tmp/`. Scripts tied to a project's tables go in `script_extend/`.
- A `script_extend/` script is one `.py` file per job; it may import stdlib, packages, `config`, `function` and the project's own `function_extend`/`files_extend` (move helpers there when a script grows); outside values only from `config.py` or the environment, in `# config`; runtime data and resume state in `tmp/<script>/`, kept while a run can resume and deleted once it succeeds.

## Verify
- `venv/bin/ruff check .`; `venv/bin/python -m unittest discover -s tests_extend -t .`; start with `venv/bin/python main.py` (startup checks catch config, duplicate `func_*` and secret errors). Windows: `venv\Scripts\` instead of `venv/bin/`.
- Database tests: a throwaway local database, dropped afterwards; never a shared or production one.
- This file is the only rules file, the same in every project; a project's feature details and business rules are in `docs_extend/<feature>.md`.
